# Authentication

How callers authenticate to MCP METRO. The metro data sources themselves need no credentials, so this is the only
authentication in the project.

## Default state: open

`config/default.yaml` ships with `webServer.auth.enabled: false`. In that state `/mcp`, `/sse` and `/api/*` answer any
request without credentials. That is intentional for local development and for the Agent Tester, and it is not safe on
a publicly reachable address — either enable authentication or keep the server behind a reverse proxy and a network
policy that restricts who can reach it.

Two endpoints stay open even when authentication is on:

- `/health` — the healthcheck the container and the proxy poll.
- `GET /api/widget-data` — the route widget's data endpoint. It is gated by the HMAC signature in the link instead of by
  a header, because the widget runs in a sandboxed iframe that cannot send credentials. See
  [Route Widget](./route-widget.md).

## Turning authentication on

```yaml
# config/local.yaml
webServer:
  trustProxy: true          # required behind an HTTPS reverse proxy, so client IPs are real
  auth:
    enabled: true
    permanentServerTokens: [ 'a-token-of-at-least-20-characters' ]
    jwtToken:
      mode: legacyAesCtr
      encryptKey: '<HS256 signing secret, 8 chars minimum>'
```

## Resolution order

The SDK inspects the `Authorization` header and takes the first method that matches:

| # | Method                  | Header form                          | Cost   | Notes                                            |
|---|-------------------------|--------------------------------------|--------|--------------------------------------------------|
| 1 | `permanentServerTokens` | `Bearer <static token>`              | O(1)   | Set lookup. For service-to-service callers.       |
| 2 | `basic`                 | `Basic base64(username:password)`    | medium | Needs both `basic.username` and `basic.password`. |
| 3 | `jwtToken`              | `Bearer <jwt>`                       | medium | Signature verification plus claim checks.         |
| 4 | `custom`                | anything                             | —      | Project-defined validator; not used here.         |

Revocation lists are checked on every path (`/mcp`, `/agent-tester`, the admin panel):
`webServer.auth.revoked.jwtTokens` accepts a full token string or a `jti`, and
`webServer.auth.revoked.users` matches the JWT payload's `user` field case-insensitively.

## JWT modes

`webServer.auth.jwtToken.mode` selects the engine. This project keeps the default.

| Mode                     | Algorithm             | Issues tokens            | Verifies              | When to use                          |
|--------------------------|-----------------------|--------------------------|-----------------------|--------------------------------------|
| `legacyAesCtr` (default) | HS256 + legacy AES-CTR| yes, locally             | yes                   | Single-server setups, backward parity |
| `embedded`               | ES256 / RS256         | yes, autogenerated keys  | yes, own JWKS         | Dev and demo with OIDC discovery      |
| `localKey`               | ES256 / RS256         | when `privateKeyPath` set| yes, PEM public key   | Isolated server with managed keys     |
| `remoteJwks`             | ES256 / RS256         | no (HTTP 501)            | yes, remote JWKS      | Corporate identity provider           |

Additional JWT switches: `checkMCPName` requires the token's service name to match this server's name; `isCheckIP`
restricts a token to the addresses listed in its `ip` claim; `issuer` stamps and enforces the `iss` claim in legacy
mode. Non-legacy modes additionally require `expectedIssuer` and mount the discovery endpoints
(`/.well-known/oauth-protected-resource`, `/.well-known/openid-configuration`, `/.well-known/jwks.json`) automatically.

## Issuing tokens

**Command line** — the usual path:

```bash
node scripts/generate-jwt.js -u <username> -ttl <N>s|<N>m|<N>d|<N>y [-s <service>] [-p "key=val;key2=val2"]

# examples
node scripts/generate-jwt.js -u admin -ttl 30d
node scripts/generate-jwt.js -u svc-bot -ttl 1y -s mcp-metro -p "role=reader"
```

The same values can come from the environment: `JWT_PAYLOAD_USERNAME`, `JWT_TTL`, `JWT_PAYLOAD_SERVICE_NAME`,
`JWT_PAYLOAD_PARAMS`. In `remoteJwks` mode the script refuses to run — tokens must come from the identity provider.

**Inside Claude Code** — the `/gen-jwt` skill wraps the same script, asks for whatever is missing, prints the decoded
payload and saves the token to `<YYYYMMDD-HHmmss>-jwt.txt`. See [SKILLS](./SKILLS.md).

**Over HTTP** — `POST /gen-jwt` with `{"username":"...","ttl":"30d","service":"...","params":"key=val"}`. Disabled by
default; enable with `webServer.genJwtApiEnable: true` (or `WS_GEN_JWT_API_ENABLE=true`). The request itself must carry
a valid `Authorization` header, so this is a way for an already-trusted caller to mint further tokens, not a public
endpoint.

**Checking a token** — `POST /ct` with `{"t":"<token>"}`. The legacy `GET /ct?t=<token>` form is rejected with HTTP 405
unless `webServer.tokenCheck.allowQueryToken` is `true`, and it is always rejected when `NODE_ENV=production`.

## Admin panel

The token-generator web UI at `/admin` is **not mounted** in this project (`adminPanel.enabled: false`). If you enable
it, note the authentication rule: with `jwtToken` among `adminPanel.authType`, the panel accepts a token only when its
payload contains `allow: 'gen-token'`:

```bash
node scripts/generate-jwt.js -u admin -ttl 30d -p "allow=gen-token"
```
